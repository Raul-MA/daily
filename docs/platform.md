# Shared platform

## Problem

Seven apps need one shell and local data boundary without conflicting navigation, styling or timer ownership. The user requires native HTML/CSS/JavaScript; review publication and Daily Pages deployment are authorized. [README](../README.md#github-pages) owns the publishing procedure; cloud setup and physical/API acceptance remain deferred.

## How It Works

- `apps/daily/index.html` and `diagnostics.html` are the two HTML entry points. CSS loads through stylesheet links. JavaScript uses explicit relative `.js` imports supported directly by browsers.
- `scripts/build.mjs` copies app/shared/module source assets unchanged into `dist/`, preserving directory structure and relative imports. It generates the manifest, SVG favicon, PNG install icons, Apple touch icon and service-worker asset list. `scripts/icons.mjs` produces the raster files using Node built-ins; application code stays unchanged and requires no icon-generation runtime. No bundler or transpiler runs. Tests, reports, sibling repos and personal exports are outside the copied paths.
- `scripts/serve.mjs` serves only the prepared directory on `127.0.0.1`. `DAILY_BASE` must match preparation and serving. Dev runs preparation once; rebuild and refresh after source edits.
- `packages/platform/src/router.js` owns the allowlisted hash routes and configurable base. IDs and query values are encoded. Unknown or malformed routes render a focused not-found heading. Routing does not create records.
- `packages/data/src/daily-state.js` manages one `daily:v1` document. Preferences are separate from versioned module payloads. `module-store.js` validates data before saving, rejects unsupported versions and preserves unrelated modules. Subscribers run only after a successful storage commit.
- Daily settings contains only shared language, dashboard widgets/quick actions and full backup controls. Its App settings directory links to app-owned destinations; no Reader or other module form mounts here. The menu’s separate Daily settings link replaces the header link, while In this app retains each app’s settings shortcut. `shell/settings-hub.js` owns the directory and Time Budget Settings deep-link selection (`#/time?section=settings`). Reader (`#/reading/settings`), Piano (`#/piano/settings`) and WhatsApp (`#/whatsapp/settings`) have dedicated routes; Plants, Coffee and Games retain their existing settings routes. Navigation never saves settings or starts sessions.
- Settings mounts `apps/daily/src/backup/view.js` for full-root export, validated preview, recovery download and explicit replacement. [Storage and migrations](storage-and-migrations.md) explains schema/reference checks, credential cleanup and failure ordering.
- The backup form and file label use bounded grid tracks so native file-input sizing cannot widen Settings or storage recovery at 320px.
- `calendar.js` schedules the next local midnight rather than a fixed 24-hour delay and rechecks date/timezone on foreground/focus. Dashboard refresh never saves records.
- `packages/ui/src/drafts.js` keeps identified forms marked `data-unsaved="true"` in memory across language renders, including file selection and focus. Conditional module form state is kept separately from domain records.
- Dashboard cards navigate; each app-linked card's icon/title opens its destination from the shared widget catalog. Running opens Time Budget; Quick actions keeps its aggregate heading and separate action links. Title links inherit the existing appearance, use a 44px target and retain shared hover/focus feedback. Settings own widget visibility/order and quick-action visibility. EN/ES changes labels without translating saved user text.
- Every page fills the available content space beside the shared sidebar, including list, form, detail, settings, Piano destinations and standalone diagnostics screens. Page-level maximum widths are removed; ordinary page padding and component/dialog sizing remain. Plants cards stay in one column of full-width rows. The header, app and footer scroll together in the document. Piano does not constrain its page to a separate viewport/scroller. `shell/theme.js` derives shared colors and font from the mounted module, watches its theme attribute and system color scheme, and resets the shell on return Home. It observes root replacements rather than timer text updates. Mouse/trackpad hover underlines links and dims enabled buttons/menus.
- `shell/sidebar.js`, `sidebar-catalog.js` and `sidebar-controls.js` provide one navigation structure for every app. At 900px and wider the sidebar reserves 248px and can collapse; narrower screens use a modal hamburger drawer with focus containment, Escape/backdrop dismissal and inert background content. Open and close controls stay on the left. The opener is an icon-only hamburger with a localized Apps accessible label and a 44px minimum target. App sections come first and a separate app-switching section sits at the bottom; outside apps, Apps starts at the top. The catalog recognizes every app detail/settings route. Menu state stays in memory; collapsing never remounts an app or writes domain data. Time Budget selects mutually exclusive mounted Time Budget, Countdowns and Settings panels; WhatsApp section controls scroll/focus existing content. Neither starts activities or changes drafts. Hidden Time Budget setup sections are unavailable during an active session.
- The shared sidebar replaces Plants' top links, Coffee's bottom tabs, Games' sidebar/bottom nav and Piano's Course/Library top links. Existing route IDs, app content/search, forms, timers and service boundaries remain. All menus use the mounted app's colors.
- `shell/footer.js` places the local-preview label, save status and PWA system information in one horizontal row, wrapping when narrow. `pwa.js` moves its retained system host into each new footer slot after renders; recovery screens without a footer retain the body fallback. Registration/update listeners are not recreated by navigation.
- `activities.js` owns persisted timestamp activity transitions. Page intervals update text only. Paused time is excluded; suspension and navigation do not pause activities. Countdown expiry does not silently complete an activity. Budget/game/piano each allow one unfinished activity.
- The single worker precaches the generated local asset list. It bypasses authenticated/external/unknown requests and deletes only `daily-pwa-` cache versions. Static cache matches ignore Vary because these are app-owned assets, never account data.
- `persistence.js` requests durable storage where available without domain writes or a retention guarantee.
- The attention screen preserves unreadable root snapshots and accepts a validated full backup after a recovery download; it never resets damaged data to empty. See [Storage and migrations](storage-and-migrations.md).
- The PWA UI offers installation help and explicit updates. It asks every open same-app tab to report its activity/form state before explicit activation. Blocked, malformed or missing replies keep the update waiting, with an explanation. Cached HTML stays pinned to its matching assets until activation.

## Gotchas

- Vite and TypeScript were used for a verified intermediate checkpoint, then replaced after the same general unit/browser checks passed. Their old reports remain historical evidence.
- `check:js` checks syntax, not types. Runtime schema validation and behavioral tests remain essential. No type-analysis claim applies to plain JavaScript.
- Generic root validation does not substitute for domain schemas. Each module adapter must validate its own payload, legacy formats and nested references before migration.
- LocalStorage has no multi-tab compare-and-swap transaction. Module saves re-read the latest document synchronously; module/form revision checks reject ordinary stale saves. The current policy supports one editing tab at a time; simultaneous cross-tab writes are unsupported. Update activation still checks every open tab.
- All seven apps are connected to the shared document. Game, budget and piano sessions save atomically with timestamp activities. Countdown controls use the registry independently. Reader credentials and disposable account caches stay outside the root; WhatsApp persists its draft before external handoff. Physical-device/API/coexistence and releases remain deferred; [progress](progress.md) records current local verification.
